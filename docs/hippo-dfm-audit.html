Hippo under dotfiles-manager

Hippo is a self-installing application that dotfiles-manager should configure, not own. Today the manager owns exactly three hippo things (the config directory link, the zsh profile file that sources hippo.zsh, and the Claude SessionStart handler). Hippo's own installer owns the runtime (binary symlink, 13 LaunchAgents, the installed brain tree, wrappers, native-messaging manifest). That split matches the manager's own contract, which excludes daemons and schedulers. Four seams need attention, ranked below; none is broken right now.

Runtime

hippo doctor exit 0
Daemon and brain running, versions aligned at 0.39.0-dev.4+gea34310, inference reachable, watchdog heartbeat 35 s. Three [WW] rows, all operational hygiene (see Operation).

Manager

dotfiles-manager doctor ok=135 warn=1
The one warning is a pending Pi AGENTS.md re-assembly, unrelated to hippo. The hippo link .config/hippo matches its ledger fingerprint.

Hippo's own knowledge base has no recorded decision on hippo as a manager module. It does record the 2026-10-16 cutover incident: after Nix removal the hippo LaunchAgents still pointed into /etc/profiles and the brain crash-looped until hippo daemon install --force.

Findings, ranked

1 · LaunchAgents freeze the install-time environment, and nothing in the sync path re-renders them

  • What: render_plist copies the installing shell's full PATH into every plist (install.rs:116) and the brain plist names /opt/homebrew/bin/uv absolutely. The live daemon plist carries a 1.1 KB PATH including /pkg/env/global/bin, .lmstudio/bin, .opencode/bin and .amp/bin.
  • Why it matters: this is the exact failure of 2026-10-16: Nix removal left the plists pointing at /etc/profiles, the brain crash-looped, and every restart ran op read, which surfaced as repeated 1Password prompts (docs/m5-cutover.md lines 472-478). dotfiles-manager doctor reported ok=136 throughout. Neither doctor checks plist contents against the current toolchain.
  • Fit with the dfm model: the manager's contract says no daemon or scheduler is part of it (docs/architecture.md line 369) and treats a launch-agent reload as disruptive (line 368). The cutover record already chose the right fix: re-run hippo's own installer. The gap is that the fix is undocumented outside the incident note, and just sync has no check that would catch the next recurrence.
  • Recommendation: record hippo daemon install --force as the owner-side repair in the dotfiles system-script docs, and add hippo doctor as a read-only check at the end of just sync, next to launch-agents.sh load. On the hippo side, rendering a minimal fixed PATH (as install:omlx already does) would remove the drift class rather than the trigger.

2 · The MCP server runs the development checkout while the daemon runs the installed brain

  • What: ~/.claude.json starts hippo-mcp with uv run --project /Users/carpenter/projects/hippo/brain hippo-mcp. The brain LaunchAgent runs uv run --no-sync --project ~/.local/share/hippo-brain. The MCP entry is declared in home/.config/mcp/machine/personal.json and generated by mcp_sync.
  • Why it matters: every MCP spawn re-syncs the dev venv and executes whatever is in the working tree, including an uncommitted migration or a branch checkout. The daemon-side require_accepted_schema guard protects the DB, but query results and tool schemas can diverge from the running brain without any doctor row saying so. Doctor's "Brain version match" compares daemon and brain server only.
  • Recommendation: point the MCP entry at the installed tree with --no-sync, matching the brain plist. This is a one-line change in the dotfiles overlay and keeps dfm as the owner. Keep a separate dev entry if you want the checkout reachable from inside the hippo repo (.mcp.json project scope).

3 · Two writers for the hippo SessionStart hook in ~/.claude/settings.json

  • What: dfm contributes the handler through the claude-settings/v1 merge (personal.session-hippo, spelled ${HOME}/…). hippo daemon install also searches for claude-session-hook.sh and rewrites the whole file through a temp-file rename when the string differs (install.rs:562-690).
  • Why it is only medium: both resolve to the same absolute string, so today each writer sees the other's result as "already correct". The cutover rehearsal already hit the ${HOME} versus absolute-path duplicate (docs/m5-cutover.md line 102) and the live apply avoided it. The merge adapter stores no hash of the live file, so hippo's rewrite does not make the dfm plan stale.
  • When it breaks: a different XDG_DATA_HOME, a brain install dir move, or a future hippo change to the hook path. Then the two writers alternate and the dfm plan reports a pending change after every mise run install.
  • Recommendation: keep dfm as the declared owner. Document the co-writer in the dotfiles README next to the Codex hooks.json note, which already describes the same pattern. If you want a single writer, the cheapest hippo-side change is a config switch that makes the installer skip the Claude hook when the path is already present; the current equality check is most of the way there.

4 · This machine is on the developer install path, which neither tool records

  • What: ~/.local/bin/hippo points at target/release/hippo inside the checkout; cargo build --release changes the running binary at the next launchd restart. The published install path (curl … install.sh, checksummed release tarball, receipts under ~/.local/state/hippo) is unused here. The brain tree is an rsync of the checkout at install time, so binary and brain can drift after a rebuild without a reinstall; the doctor version rows catch that case.
  • Fit: INVENTORY.md's update rule ("one package/service/update owner per component", DESIGN.md line 267) means the future dotfiles-manager update should report hippo as native-owned and held, like Firstmate, rather than attempt a version bump. The dev-symlink model makes "installed version" a property of the working tree, which the manager cannot inventory.
  • Recommendation: no change to the mechanism. Write down which path this machine uses and that the recovery command after any environment change is mise run install from the checkout. If you later want the manager's update to cover hippo, switch this machine to the release installer so a version pin exists to compare against.

5 · Operation: green, with hygiene items

  • Enrichment: 1 pending, 3 failed queue items, 3 failed classifications. Not growing; inspect with the failed-queue query in the monitoring skill.
  • Alarms: 466 auto-resolved alarms pending prune (hippo alarms prune). Doctor marks this [--], not a failure.
  • Idle sources: opencode 22 d, cursor 5 d, pi 5 d. Doctor suppresses them as idle; the freshness rows still print [WW], so the exit code stays 0 but the output looks worse than it is.

How hippo fits the manager's model

The manager's own documents already classify this case. INVENTORY.md lists Hippo under "Personal and homelab" module content, and lists launchd resources under "Platform/system" with "separate privileged adapters and explicit ownership handoffs". Its Firstmate row is the template: "Native application owns these. The manager can own selected declarative launch/config files and issue explicit update requests." Hippo is the same shape.

What would be wrong

Making hippo a dfm module that links the plists

The maxfiles agent uses this pattern (dfm links the plist, launch-agents.sh load bootstraps it). It fits a static plist. Hippo's plists are rendered from the installing environment and from config.toml, and the installer also writes wrappers and the brain tree. Splitting that across two owners recreates the cutover failure with a second actor.

Letting hippo's installer own the config directory

The config is now git-tracked and reviewed through the dfm plan. The installer already respects that: it only seeds defaults when the files are absent. Keep it that way.

Treating a green dfm doctor as proof hippo works

It proves three links. The runtime authority is hippo doctor, which checks versions, launchd, sockets, inference, queues and source freshness in under 2 s.

Left out, and where to look next

  • No side-channel script was executed, not even in --check mode. The Codex hook and MCP outputs were read from their live files.
  • The Kaneo DFM-52 section 12 comment that holds the incident evidence was not opened; the m5-cutover record was used instead.
  • mcp_sync behaviour on ~/.claude.json was taken from docs/ai-tools/mcp-setup.md, not from the Python source.
  • Whether the Firefox extension is loaded in a non-Dev-Edition profile was not verified; only the fresh browser capture row supports that inference.
